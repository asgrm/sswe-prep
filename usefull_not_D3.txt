
41. Name Undici network & connection errors (most relevant to connection failures)

  UND_ERR_CONNECT_TIMEOUT — connection timed out

  UND_ERR_SOCKET — socket/TCP error or drop

  UND_ERR_HEADERS_TIMEOUT — headers not received in time

  UND_ERR_BODY_TIMEOUT — response body too slow

42. Name Undici content length mismatch errors (typically retryable)

  UND_ERR_REQ_CONTENT_LENGTH_MISMATCH — request body ≠ declared length

  UND_ERR_RES_CONTENT_LENGTH_MISMATCH — response body ≠ declared length

43. Name Undici infrastructure errors

  UND_ERR_DESTROYED — client already destroyed

  UND_ERR_CLOSED — client already closed

  UND_ERR_BPL_MISSING_UPSTREAM — no upstream server available

44. Name Undici protocol errors

  UND_ERR_HEADERS_OVERFLOW — headers too large

  UND_ERR_RES_EXCEEDED_MAX_SIZE — response too large

  UND_ERR_TRAILER_MISMATCH — invalid/mismatched trailers

45. Which Undici abort error is NOT retried?
  UND_ERR_ABORTED — request explicitly cancelled

44. Usage of duplexPair for teesing a custom protocol implementation
  Let's say you have a simple length-prefixed message protocol:
  const { duplexPair } = require('node:stream');

  // Protocol: 4 bytes length header + message body
  class ProtocolServer {
    constructor(socket) {
      this.socket = socket;
      socket.on('readable', () => this._onReadable());
    }

    _onReadable() {
      const header = this.socket.read(4);
      if (!header) return;

      const length = header.readUInt32BE(0);
      const body = this.socket.read(length);
      if (!body) return;

      const message = JSON.parse(body.toString());
      this._handleMessage(message);
    }

    _handleMessage(message) {
      // echo back with server timestamp
      const response = JSON.stringify({
        ...message,
        serverTime: Date.now()
      });
      const buf = Buffer.from(response);
      const header = Buffer.alloc(4);
      header.writeUInt32BE(buf.length);
      this.socket.write(Buffer.concat([header, buf]));
    }
  }

  class ProtocolClient {
    constructor(socket) {
      this.socket = socket;
    }

    send(message) {
      const buf = Buffer.from(JSON.stringify(message));
      const header = Buffer.alloc(4);
      header.writeUInt32BE(buf.length);
      this.socket.write(Buffer.concat([header, buf]));
    }

    async receive() {
      return new Promise((resolve) => {
        this.socket.once('readable', () => {
          const header = this.socket.read(4);
          const length = header.readUInt32BE(0);
          const body = this.socket.read(length);
          resolve(JSON.parse(body.toString()));
        });
      });
    }
  }

  // --- test ---
  async function test() {
    const [clientSocket, serverSocket] = duplexPair();

    const server = new ProtocolServer(serverSocket);
    const client = new ProtocolClient(clientSocket);

    client.send({ type: 'ping', payload: 'hello' });
    const response = await client.receive();

    console.log(response);
    // { type: 'ping', payload: 'hello', serverTime: 1234567890 }
  }

  test();
  The point here: ProtocolServer and ProtocolClient have zero knowledge they're talking to each other in-process. They just see a socket-like Duplex — same code would work with a real net.Socket. duplexPair gives you a real stream with backpressure, buffering, and readable/writable mechanics, so your protocol logic is exercised exactly as it would be in production.
