1)
An engineer's exploration subagent spent 30 minutes analyzing a legacy payment system, reading 47 files and documenting data flows. The session was interrupted when the engineer's connection dropped. While away, a teammate merged a PR that renamed two utility functions. The engineer wants to continue the same exploration.
What's the most effective approach?

Your answer: C. Launch a fresh subagent with a summary of prior findings.

Correct: D. Resume the subagent from its previous transcript and inform it about the renamed functions.

Correct. Keep the accumulated understanding, and give it a targeted delta about the renames so it can update its mental model — minimum waste, maximum accuracy.

Principle: When an interruption invalidates only a small, specific piece of accumulated context, the right move is targeted correction, not wholesale restart. Restarting is appropriate when the context itself is suspect or too stale to trust — not when it's 99% intact and you just need to patch a couple of facts.

2)
Your extraction pipeline processes invoices and extracts line items, subtotals, tax amounts, and grand totals. During evaluation, you discover that in 18% of extractions, the sum of extracted line item amounts doesn't match the extracted grand total—sometimes due to OCR errors in the source document, sometimes due to extraction mistakes by the model. Downstream accounting systems reject records with mismatched totals.
What's the most effective approach to improve extraction reliability?

Your answer: C. Add few-shot examples demonstrating invoices where extracted line items sum correctly to the stated total, encouraging the model to produce mathematically consistent extractions.

Correct: A. Add a "`calculated_total`" field where the model sums extracted line items alongside a "`stated_total`" field. Flag records for human review when values differ.

Correct. Capturing both values makes the discrepancy a first-class signal — you catch OCR errors and extraction mistakes uniformly, and you can route only the mismatched 18% to humans.

Principle: when correctness can't be guaranteed by the model, make the failure mode observable rather than trying to prompt it away.

What exploration strategy will most effectively build understanding, given Claude built-in tools and context limits?

Your answer: B. Launch parallel subagents to explore different services simultaneously, then synthesize their findings into an architectural overview.

Correct: C. Use Grep to find authentication entry points, read those files, then follow imports and function calls to map the auth flow incrementally.

Correct. Start at entry points (login, token verify, middleware), then trace outward following real code edges. Incremental, grounded, fits within context limits.

Principle: when the goal is to build one coherent mental model of how a system works, explore by following the system's actual structure (call graphs, imports, control flow) incrementally — don't parallelize on an artificial partition and stitch the pieces back together after the fact. Parallelize exploration when subtasks are truly independent and coverage is the goal.

Your answer: D. First call `get_customer` and `lookup_order` to gather account context, then escalate to a human agent.

5)
Your agent needs to insert a new helper function into the middle of a 150-line utility module, between two existing functions. The Edit tool fails because its `old_string` parameter cannot find unique text to match — the file has repetitive docstrings, variable names, and structural patterns.
What's the most reliable way to complete this insertion?

Your answer: A. Use Edit with an extremely long `old_string` capturing 30+ lines of context to guarantee uniqueness

Correct: D. Use Read to load the file, add the function at the appropriate location, then Write the updated file

Correct. When Edit's unique-match contract can't be satisfied in a repetitive file, fall back to Read → modify in memory at the intended line → Write the full file back.

Principle: When a tool requires a precondition to hold (uniqueness, well-formedness, a specific structural assumption) and the actual input doesn't reliably satisfy that precondition, don't try to force satisfaction by scaling up the same approach (more context, more retries, more text) — recognize the mismatch and switch to an approach that doesn't depend on the precondition at all. Brute-forcing around a structural constraint is fragile; sidestepping the constraint is robust.

6)
During a billing dispute resolution, your agent successfully retrieves customer info via `get_customer` and order details via `lookup_order`, but when attempting to call `process_refund`, the tool returns a timeout error. The agent has enough information to explain the charges and verify refund eligibility, but cannot actually process the refund due to the backend failure.
What approach best balances first-contact resolution with appropriate error handling?

Your answer: B. Implement automatic retries with exponential backoff for `process_refund`, keeping the conversation open until the refund is successfully processed

Correct: C. Explain the billing, confirm refund eligibility, acknowledge the system issue preventing immediate processing, and offer escalation or retry later

Correct. Deliver the partial value you can (explanation + eligibility), be honest about the failure, and let the customer choose between human escalation or a retry. Classic graceful degradation.

Principle: When a multi-step task partially succeeds and partially fails due to a backend/tool failure, don't let the failed step gate the entire response. Deliver whatever value the successful steps already produced, state plainly what failed and why (to the extent known), and offer the person a choice for how to handle the blocked part — rather than silently retrying and making them wait with no visibility, or discarding the successful work along with the failed part.

7)

A customer raises three separate issues during one session: a refund inquiry (turns 1-15), a subscription question (turns 16-30), and a payment method update (turns 31-45). At turn 48, the customer asks "What happened with my refund?" The conversation is approaching context limits.
What strategy best maintains the agent's ability to address all issues throughout the session?

Your answer: A. Extract and persist structured issue data (order IDs, amounts, statuses) into a separate context layer.

Correct: C. Summarize earlier turns into a narrative description, preserving full message history only for the active issue.

Correct. Progressive summarization compresses stable resolved topics while keeping the active thread verbatim — the classic pattern for long multi-issue conversations near the context limit.

Principle: When compressing history near a context limit across multiple sequential subtopics, compress based on recency and activity status (older/resolved → summarized, active → verbatim), not by narrowing to a fixed schema of fields extracted from the whole conversation. Schema extraction is useful as a supplement for hard facts you know you'll need (like an order ID), but it isn't a substitute for narrative compression, because it silently drops everything outside the schema that a follow-up question might depend on.

8)

Your extraction system implements automatic retries when validation fails. On each retry, the specific validation error is appended to the prompt. This retry-with-error-feedback approach resolves most failures within 2-3 attempts.
For which failure pattern would additional retries be LEAST effective?

Your answer: A. The model extracts keywords as a nested object organized by category when the schema requires a flat array of strings

Correct: D. The model extracts "et al." for co-authors when the full list exists only in an external document not in the input

Correct. No amount of retrying teaches the model information that isn't in the input. Retry-with-error-feedback only fixes mistakes the model could have gotten right from the source.

Principle: retry-with-error-feedback only fixes failures caused by the model misinterpreting or misformatting information it already has access to — it can't fix failures caused by the required information being absent from the input entirely.

Compliance without transparency isn't actually honoring the request if it withholds a materially better path from someone who would probably want to know about it.

11)

12)
Two sub-agents return conflicting figures for the same metric, each with moderate confidence. Before the coordinator writes the final answer, the best move is to:

Your answer: D. Include both numbers in the final answer and let the reader decide.

Correct: C. Run a focused check that re-fetches the metric from the primary source and resolves the conflict before synthesizing.

When two internal outputs disagree on a factual point and verification is available and cheap, verify and resolve before finalizing — don't present unresolved internal disagreement to the end user as if it were their responsibility to adjudicate. Reserve "present both sides" for cases of genuine, irreducible ambiguity (where authoritative sources themselves disagree), not for cases where your own pipeline just hasn't finished checking its work.

13)

Your answer: B. Analyze imports and class hierarchies to identify the base cache class, Read that file to understand the interface, then trace specific invalidation implementations.

Then navigate outward only along the paths relevant to your actual task, rather than reading exhaustively or parallelizing across an artificial partition. This keeps context spend proportional to relevance, not to the system's total size.

14)
The document analysis agent has a single `analyze_document` tool that takes a document and a free-text instruction parameter. During evaluation, requests like "extract the key financial metrics" often return narrative summaries, while "summarize the methodology" sometimes returns raw data tables. The synthesis agent reports that 35% of analysis results require re-requests with clarified instructions.
What's the most effective way to improve reliability?

Your answer: A. Split the generic tool into purpose-specific tools—`extract_data_points`, `summarize_content`, `verify_claim_against_source`—each with defined input/output contracts.

Correct. Free-text instructions put the semantics in prose, which the model interprets inconsistently. Purpose-specific tools give the model an explicit, well-typed contract to pick between.

Principle: When a single tool's behavior is disambiguated only by free-text instructions, and you're seeing inconsistent outputs across similar-sounding requests, the fix is usually to move the semantics out of prose and into structure — split the tool by intended output/purpose so each has an explicit contract. This is the same shape as "give the model a schema instead of hoping it infers one": constraints at the interface level are far more reliable than constraints expressed only in natural language instructions.

15) Your extraction pipeline processes restaurant menus and must output structured JSON with fields for item names, descriptions, prices, and dietary tags. Some menus use inconsistent formatting—prices as "$12" vs "12.00", dietary info as icons vs text.
What's the most reliable approach?

Your answer: B. Extract data as-is and normalize formats in post-processing code after Claude returns.
